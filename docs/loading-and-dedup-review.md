# Loading 场景与文件去重实现说明

本轮已按确认后的范围实施浏览器直传、文件指纹去重和编辑器等待态，直传接口与安全边界见 [直传说明](browser-direct-upload.md)。

## Loading 场景

范围包括用户端和仓库内独立的 admin-frontend。优先级用于建议实施顺序，不代表所有页面都应整页遮罩。

| 优先级 | 场景及代码位置 | 现状 | 建议 |
| --- | --- | --- | --- |
| P0 | PDF/DOCX/Markdown 导入，`KnowledgeBasePage.vue` | 已有阶段文字、按钮禁用和解析轮询 | 已实现准备、指纹、上传、确认、提交解析、解析中的阶段文字；解析无可靠百分比时显示转圈语义。超时保留任务号，允许稍后重试查询 |
| P0 | 图片、音视频、附件上传，`MarkdownEditorAdapter.vue` | 已有逐文件 spinner、失败重试/移除，并阻止未完成时发布 | 保留逐文件反馈，与直传状态统一；有真实传输进度时显示百分比，不整页锁定编辑器 |
| P0 | 打开编辑器加载草稿，`PageEditor.vue` | 异步读取草稿 | 已增加覆盖编辑区域的加载态；加载完成前遮挡编辑操作并禁用保存，避免晚到的草稿覆盖用户输入 |
| P0 | 保存草稿，`PageEditor.vue` | 保存请求没有独立状态 | 已增加“保存中”、防重复提交和非冲突错误提示；保存失败时发布流程停止 |
| P0 | 生成发布说明、保存并发布，`PageEditor.vue` | 发布按钮显示“发布中” | 拆分“生成说明 / 保存 / 发布”阶段；弹窗内 loading，失败保留输入 |
| P0 | Markdown/HTML 导出，`PageEditor.vue` | exporting 禁用导出菜单项 | 工具栏导出按钮在等待期间显示“导出中…”并禁用重复操作 |
| P1 | 获取版本历史、恢复历史版本，`WorkspacePage.vue` | 历史列表请求完成后才展开；恢复无独立 pending | 立即打开抽屉并显示骨架；恢复按钮显示 pending；错误与空历史区分 |
| P1 | 加载文档、目录、知识库、设置、回收站、通知、会话历史 | 各处已有 loading 变量或“正在加载”文字 | 统一局部骨架/转圈与错误重试，不重复建设全屏 loading；翻页/追加列表保留旧数据 |
| P1 | 源 PDF/DOCX 下载与渲染，`SourcePreview.vue` | 已有加载状态、取消及错误提示 | 统一视觉，并区分获取文件和渲染文件；不能仅在请求完成就结束 loading |
| P1 | 邀请、成员操作、审核、权限转交、通知全部已读 | 创建邀请/部分设置已有 saving，`CollaborationPanel.vue` 的部分操作及 `NotificationCenter.markAll` 无独立 pending | 按操作或按行显示 loading 和防重复提交，不阻塞整个工作空间 |
| P1 | 管理端创建/修改索引、重建、校验、切换、删除、暂停/恢复，`admin-frontend/src/views/IndexManagementView.vue` | 已有列表加载及后台轮询，操作函数缺少统一命令 pending | 操作按钮/弹窗 loading；后台重建显示已有任务状态和进度，命令返回不等于重建完成 |
| 保留 | AI 问答生成，`ConversationMessages.vue` | 已有生成中反馈、检索过程、停止操作 | 保留流式反馈，补足首个事件到达前的等待态；不加遮挡回答的整页 loading |

通用建议：请求开始立即防重复提交；明显耗时操作立即显示状态，短操作可延迟约 200ms 显示 spinner 以避免闪烁。成功、异常、取消都结束对应状态；并发请求各自维护状态，后台轮询不触发全局遮罩。纯本地知识库/目录过滤无需网络 loading。

## 浏览器哈希可行，前缀只能筛选候选

浏览器可读取用户选择的 File，在本机计算 SHA-256，向 kwiki 仅发送摘要和大小，无需把文件传给 kwiki。实现使用 Web Crypto 的 SHA-256；当前单文件上限为 20 MB，若低端设备实测出现明显卡顿，再把完整哈希迁移到 Web Worker。见 [MDN digest 文档](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/digest)。

按用户确认，采用 **前 1 MiB（1,048,576 字节）的 SHA-256 + 文件总大小**初筛；首次上传的新文件也在浏览器计算完整 SHA-256 并保存，供后续命中时比较。小于等于 1 MiB 的文件，初筛哈希就是完整哈希，直接复用。

现有文件均为测试数据，由用户自行删除后重新上传。本方案不包含旧文件迁移或历史哈希补算，也不执行测试数据删除。

流程如下：

1. 浏览器先读取前 `min(文件大小, 1 MiB)` 字节计算 SHA-256，仅提交前缀哈希、总大小和规则版本。
2. 前缀和大小无候选时，浏览器再计算完整 SHA-256，文件通过预签名地址直传云端；上传完成确认后，保存前缀哈希、完整哈希、大小和物理文件关联。
3. 前缀和大小有候选时，浏览器才计算整个文件的 SHA-256，与候选文件已经记录的完整哈希比较；多个同前缀、同大小的候选必须分别匹配。
4. 完整哈希不同：作为新文件直传并保存两种哈希；相同：当前实现直接创建当前用户的 attachment 引用并复用已验证 blob。

**同样大小、同样前缀不代表完整文件相同。** 两个分支最终都会计算完整哈希：首次上传为建立记录，候选命中为精确比较。因此前缀初筛用于分流查重流程；它把完整哈希计算放在上传初始化之后，未命中时不会先做候选比较。无须云端按需补算候选文件的哈希，但浏览器声明的摘要仍需按下文进行可信校验。

## 表和索引建议

实际实现使用独立的物理文件表 `attachment_blob`：

| 字段 | 用途 |
| --- | --- |
| id | BIGINT 主键 |
| hash_version | 哈希算法/取样规则版本 |
| full_sha256 | BINARY(32)，以 SHA-256 原始 32 字节保存；首次上传时由浏览器计算 |
| byte_size | BIGINT，总字节数 |
| prefix_sha256 | BINARY(32)，以 SHA-256 原始 32 字节保存 |
| prefix_bytes | 当前由 `hash_version=sha256-prefix-1m-v1` 固定表示 `min(byte_size, 1048576)` |
| content_type | 首次上传时保存的对象 MIME；完整哈希唯一键不依赖它 |
| content_center_file_id | 唯一物理文件标识 |
| status | 当前为 `PENDING` 或 `STORED`；只有 `STORED` blob 可被跨用户复用 |

- 最终唯一键：`(hash_version, full_sha256, byte_size)`。
- 前缀初筛使用普通非唯一索引：`(hash_version, prefix_sha256, byte_size)`。
- 保留每位用户/每个知识库自己的 attachment、文件名、文档、权限和解析关系，只让 attachment 指向共享 blob。
- V27 已移除 `attachment.content_center_file_id` 的唯一约束，新增 `attachment.blob_id` 指向共享物理文件；旧测试附件不回填指纹，删除后重新上传即可。
- 并发上传均未命中时可能产生临时重复对象，需要在完整哈希验证完成后以唯一键和引用迁移收敛；前缀索引不能设成唯一键。清理以有效引用为准，不能因为某位用户删除文档就删除共享对象。

MySQL InnoDB 的这类索引采用 B-tree。精确查找不扫描全部文档，见 [MySQL 索引说明](https://dev.mysql.com/doc/refman/8.4/en/mysql-indexes.html)。

## 能支撑多少文件、需要多久、是否加缓存

没有“超过固定文件数索引就失效”的阈值。百万至千万条可作为单 MySQL 实例的设计量级，是否达到目标取决于磁盘、buffer pool、并发 QPS、行宽与写入量；上亿条也不是逻辑上不可行，但需要实测容量和运维设计。

粗略容量估算：单个二级索引条目仅 32 字节哈希 + 8 字节大小 + 8 字节主键已经是 48 字节，还未计入版本、记录头、页空隙和 B-tree 开销。一个此类索引可按每百万条约 0.1 GB、每千万条约 1 GB 的量级做初步预算，实际可能明显不同；前缀和全量两个索引需分别计费，表数据另算。

延迟不以文档数单独承诺。热索引、低争用的本地查询通常可争取毫秒级；可以先把查重 API 的 p95 < 50ms 作为压测目标（不含浏览器哈希、广域网 RTT 和文件上传），这不是当前项目测量结果。

**第一版不建议加 Redis 查重缓存。** 先使用数据库唯一索引和 InnoDB buffer pool；观察查询 p95、QPS、buffer pool 命中率及慢查询。确有热点或数据库压力再加缓存，缓存不能取代唯一约束和状态校验，也不应长期缓存“未找到”。浏览器哈希时间应在低端手机和目标 PC 上实测，不能用服务器哈希跑分代替。

## 跨用户复用的校验边界

浏览器计算哈希可行，但服务器不能仅凭浏览器提交的 hash 就认定文件真实存在或把别人的私有文档授予当前用户。摘要并不是访问权限或持有文件的证明。

当前实现已经做到：

1. **节省存储**：首次上传完整哈希进入 `attachment_blob`；后续相同完整哈希直接创建当前用户的 attachment 引用，不经过 kwiki 文件中转。
2. **访问隔离**：复用只返回当前用户/知识库自己的 attachment UUID，下载和媒体预览仍经过原有知识库权限校验。

当前内容中心 SDK 0.1.3 的直传接口没有暴露完整 SHA-256 checksum 参数，因此服务端无法独立证明浏览器提交的摘要与对象字节一致。上线到不完全可信的客户端环境前，应让内容中心支持 checksum 校验或增加持有证明/挑战机制；这属于后续加固，不影响浏览器直传和当前测试环境的去重实现。S3 预签名上传的 checksum 能力见 [AWS 预签名上传文档](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)，具体能力需以实际云供应商为准。

当前实现采用前 1 MiB SHA-256 + 总大小初筛、首次上传记录完整 SHA-256、命中后完整 SHA-256 检查、物理文件共享表和 MySQL 索引，暂不加入 Redis 查重缓存。
